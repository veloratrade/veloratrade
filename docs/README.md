> ### ۵ قاعده‌ای که هرگز نقض نمی‌شوند
>
> 1. **بدون تأیید صریح مالک، هیچ تغییری اعمال نکن** — نه commit، نه push، نه اجرای workflow. «دسترسی داشتن» مجوز نیست (NP-1).
> 2. **Production را لمس نکن.** نه انتشار، نه POST، نه Secret اضافه‌کردن.
> 3. **تعارض را گزارش کن، تفسیر نکن.** اگر سند با کد یا با دستور مالک نخواند، بایست و بپرس.
> 4. **ادعا نکن — اثبات کن.** هر گزارش وضعیت باید شاهد اجرایی داشته باشد (شماره run، خروجی API، کد وضعیت).
> 5. **رمز نخواه.** به مقدار هیچ Secret نیازی نداری و دسترسی هم نداری. `${{ secrets.NAME }}` کافی است.
>
> ### گام صفر — وضعیت زنده را بگیر (~۲۰ ثانیه)
>
> ```bash
> bash tools/velora-status.sh          # گزارش خوانا
> ```
>
> ### 🔴 قرارداد اثبات اجرا — این بند اختیاری نیست
>
> اسکریپت در انتها یک کد یکتا چاپ می‌کند: **`VELORA-RUN-xxxxxxxx`**
>
> **اولین پیام تو به مالک باید با همین کد شروع شود.** این کد از HEAD، ساعت جاری و
> شمار فایل‌ها ساخته می‌شود؛ حدس‌زدنی نیست و از روی این سند قابل بازسازی نیست.
>
> | حالت | معنا |
> |---|---|
> | کد را نوشتی | گام صفر واقعاً اجرا شد ✅ |
> | کد را ننوشتی | **گام صفر پریده شده.** مالک باید گزارش را رد کند و اجرای اسکریپت را بخواهد |
> | «اجرا کردم» ولی بدون کد | طبق BR-6 ادعای بدون شاهد است — بی‌اعتبار |
>
> اگر اسکریپت اجرا نشد (نبود دسترسی، خطا)، **همان را صریح بگو** — ادعای وضعیت
> بدون اجرا ممنوع است. سکوت دربارهٔ نبود کد، خودش نقض BR-6 است.
>
> **درس ۲۰۲۶-۰۸-۱۷ (چرا این بند اضافه شد):** یک جلسه به‌جای اجرای اسکریپت، خودش
> چند فراخوانی دستی به API زد. نتیجه ناقص بود: وضعیت اجرای workflowها و
> protection rules دیده نشد و کهنه‌بودن §7 دیر کشف شد. سند «گفتنِ» گام صفر را
> داشت ولی هیچ راهی برای **تشخیص نقض** نداشت. حالا دارد.
>
> این اسکریپت **فقط‌خواندنی** است و وضعیت واقعی را از git و API می‌خواند:
> کامیت جاری، هر ۸ workflow و آخرین اجرایشان، Environment و protection rules،
> نام Secretها (**هرگز مقدار**)، سلامت دو محیط، و backlog. برخلاف متن سند،
> **هیچ‌وقت کهنه نمی‌شود**.
>
> `docs/PROJECT_STATE.json` همان خروجی به شکل ماشین‌خوان است — یک **snapshot**،
> نه منبع حقیقت. اگر `_meta.generated_from_commit` با HEAD فعلی فرق دارد،
> کهنه است؛ با `bash tools/velora-status.sh --json > docs/PROJECT_STATE.json`

#### قاعدهٔ Secret — برای جلوگیری از پرسش تکراری

**agent هرگز به مقدار رمز نیاز ندارد و دسترسی به آن هم ندارد.** GitHub مقدار Secret
را از REST API برنمی‌گرداند (حتی با توکن `admin: true`)؛ فقط نام و تاریخ را می‌دهد.
مقدار صرفاً هنگام اجرا داخل runner تزریق و در لاگ ماسک می‌شود. نوشتن
`${{ secrets.NAME }}` در workflow کافی است.
**فرستادن رمز در چت هیچ قابلیتی اضافه نمی‌کند و فقط یک نشت جدید است (NP-2).**

## 4. Runbook — عملیات استاندارد

### RB-1: استقرار مجدد Staging
```
پیش‌شرط: تغییرات روی برنچ main باشد
اجرا:     GitHub → Actions → "Deploy Staging" → Run workflow (ref: main)
Secrets:  خودکار خوانده می‌شوند — نیازی به credential نیست
پس‌شرط:   اجرای کامل RB-3
```

### RB-2: به‌روزرسانی env استیجینگ
```
1. مقدار جدید کامل env → Secret «STAGING_VELORA_ENV» (Settings → Secrets → Actions)
2. GitHub → Actions → "Setup Staging Private Root" → Run workflow
3. راستی‌آزمایی: /health باید 200 برگرداند
⚠️ الزامات فرمت: JWT_SECRET ≥ 32 chars | APP_ENCRYPTION_KEY = base64 دقیقاً 32 بایت | CORS بدون wildcard
```

### RB-3: راستی‌آزمایی پس از استقرار (Smoke Suite)

**ساختار (از ۲۰۲۶-۰۸-۱۷):** منطق بررسی فقط در یک فایل زندگی می‌کند تا بین محیط‌ها شکاف نیفتد.

```
healthcheck-suite.yml        ← تنها محل منطق مشترک (workflow_call، مستقیم اجرا نمی‌شود)
   ├── healthcheck-staging.yml      wrapper نازک → staging  + write_probes=true
   └── healthcheck-production.yml   wrapper نازک → production + گارد تأیید
```

| محیط | نحوه اجرا | probe نوشتاری |
|---|---|---|
| Staging | Actions → «Health Check (Staging)» → Run workflow | ✅ فعال — محیط امن، DB مستقل |
| Production | Actions → «Health Check (Production)» → Run workflow | ⛔ فقط با نوشتن دقیق `WRITE-TO-PRODUCTION` در ورودی `confirm_production_writes` |

- **قاعده نام‌گذاری:** نام فایل workflow باید دامنه‌اش را اعلام کند (درس OC-7).
- **افزودن بررسی جدید:** فقط در `healthcheck-suite.yml`. تفاوت‌های محیطی با شرط `IS_STAGING` مدل می‌شوند (مثلاً استیجینگ باید `noindex` بدهد و تولید نباید).
- **probe نوشتاری چرا حذف نشد:** تست گارد same-origin ذاتاً به درخواست تغییردهنده نیاز دارد؛ با GET تبدیل به تست تزئینی می‌شود.
- ⚠️ اجرای این تست‌ها از سندباکس چت ممکن نیست (OC-1/OC-6).

**۱۲ بررسی خواندنی** (هر دو محیط، مگر ذکر شود):

| تست | Staging | Production |
|---|---|---|
| `GET /health` | 200 + **`data.status == "ok"`** (پاکت B-8) | همان |
| `GET /fa/` و `/en/` | 200 | همان |
| `GET /` | 200 + هدر `X-VELORA-Locale` | همان |
| `GET /dashboard` بدون سشن | 302 → `/fa/login/` (اثبات اتصال DB) | همان |
| `GET /api/.env` | 403/404 + اسکن بدنه برای نشت | همان |
| `GET /locale-router.php` مستقیم | 403/404 | همان |
| `robots.txt` | `Disallow: /` | در دسترس (ایندکس مجاز) |
| هدر `X-Robots-Tag` | `noindex, nofollow` | **نباید** noindex باشد |
| هدر CSP | موجود | همان |
| `sitemap.xml` | **404 — عمداً نیست** | **200 — باید باشد** |
| مسیر ناموجود | 404 | همان |

**۳ probe نوشتاری** — استیجینگ آزاد؛ تولید فقط با `WRITE-TO-PRODUCTION`:
Origin جعلی → 403 • logout با Origin درست → `loggedOut:true` • تطابق هش منیفست (فقط تولید)


#### RB-6: طرح بازگشت تولید (Rollback) — پیش‌نویس

> **وضعیت: پیش‌نویس، تأییدنشده.** پیش از اولین انتشار تولید باید نهایی شود.
> اولویت اعلامی مالک: «امنیت و قابلیت rollback مهم‌تر از سرعت انتشار».

**آنچه به نفع ماست (راستی‌آزمایی‌شده):**

| واقعیت | پیامد |
|---|---|
| `mirror -R` **بدون** `--delete` است | انتشار فقط بازنویسی/افزودن می‌کند؛ **هیچ فایلی حذف نمی‌شود** |
| `dangerous-clean-slate: false` | همان تضمین در ابزار فعلی |
| `api/.env` و `api/storage/**` در exclude | داده و secret سرور دست‌نخورده می‌ماند |
| هر انتشار از یک کامیت مشخص (NP-6) | نسخهٔ قبلی همیشه در git موجود است |

**پیامد مثبت:** یک انتشار خراب، داده را از بین نمی‌برد — فقط فایل‌ها را کهنه/جدید می‌کند.
**اما:** چون حذفی رخ نمی‌دهد، فایلی که در نسخهٔ جدید حذف شده باشد روی سرور **باقی می‌ماند**.
یعنی بازگشت با انتشار مجدد، وضعیت را دقیقاً به قبل برنمی‌گرداند.

**سه گزینهٔ بازگشت:**

| # | روش | زمان | پوشش |
|:--:|---|---|---|
| R-1 | **انتشار مجدد از کامیت قبلی** — `workflow_dispatch` با `ref` کامیت سالم | ~۵ دقیقه | فایل‌های تغییرکرده ✅ / فایل‌های اضافه‌شده ❌ |
| R-2 | **بکاپ cPanel پیش از انتشار** — snapshot از `public_html/` | بسته به حجم | کامل ✅ |
| R-3 | **بکاپ خودکار در خود workflow** — `tar` از docroot به مسیر خارج از web root پیش از mirror | ~۱ دقیقه | کامل ✅ ولی فضای دیسک مصرف می‌کند |

**پیشنهاد:** ترکیب **R-3 + R-1**. یک مرحلهٔ بکاپ در ابتدای job تولید (پیش از هر نوشتنی)
که خروجی را در `/home/piknet/velora_backups/pre-deploy-{sha}.tar.gz` بگذارد، به‌علاوهٔ
امکان انتشار مجدد از کامیت قبلی. هر دو بدون وابستگی به cPanel کار می‌کنند.

**مسائل باز:**
- سیاست نگهداری بکاپ (چند نسخه؟ پاکسازی خودکار؟)
- فضای دیسک حساب — باید پیش از فعال‌سازی بررسی شود
- بازگردانی دیتابیس **در این طرح نیست** — انتشار فایل، schema را تغییر نمی‌دهد؛
  هر migration نیازمند طرح بازگشت جداگانه است (NP-3)


#### RB-7: انتشار تولید (Production Release) — رویهٔ مصوب

> **مدل تأییدشدهٔ مالک (۲۰۲۶-۰۸-۱۷):** انتشار خودکار انجام می‌شود، ولی
> **هر بار با تأیید صریح مالک** و تنها زمانی که CI و استیجینگ سبز باشند.

**زنجیرهٔ اجرا — هر حلقه پیش‌شرط بعدی است:**

```
gate          عبارت CONFIRM-PRODUCTION-DEPLOY  ← اگر غلط باشد هیچ اتصالی برقرار نمی‌شود
  ↓
staging_gate  Smoke Suite روی استیجینگ (فقط GET)  ← استیجینگ خراب = تولید متوقف
  ↓
guard         csp-guard.yml (تطابق منیفست و صفحات)
  ↓
deploy        ساخت بستهٔ allow-list → ۱۱ گارد → بکاپ → انتقال
  ↓
healthcheck   healthcheck-production.yml (خودکار)
```

**اجرا:** Actions → «Deploy Production» → Run workflow

| ورودی | مقدار |
|---|---|
| `confirm_production_deploy` | دقیقاً `CONFIRM-PRODUCTION-DEPLOY` |
| `dry_run` | **پیش‌فرض `true`** — فقط فهرست می‌کند. برای انتشار واقعی به `false` تغییر دهید |

**چرا `dry_run` پیش‌فرض روشن است:** اگر کسی سهواً workflow را اجرا کند، بدترین
اتفاق یک گزارش فهرست است، نه نوشتن روی سایت زنده. انتشار واقعی نیازمند **دو**
اقدام آگاهانه است: نوشتن عبارت تأیید **و** خاموش‌کردن dry-run.

**بکاپ:** پیش از هر نوشتن، کل docroot دانلود و به‌عنوان artifact نودروزه
(`pre-deploy-backup-{sha}`) ذخیره می‌شود. **بکاپ خالی = توقف اجرا** — چون یعنی
مسیر یا اتصال مشکل دارد و ادامه یعنی انتشار بدون راه بازگشت.

**دست‌نخورده روی هاست:** `api/.env` • `api/storage/` • `velora_private/`

## 8. پروتکل شروع جلسه جدید (Session Bootstrap Protocol)

### ورودی موردنیاز از مالک

```
① دسترسی به مخزن   ② جمله: «طبق docs/README.md ادامه بده»
```

> 🔴 **هشدار امنیتی (درس ۲۰۲۶-۰۸-۱۷):** نسخهٔ قبلی این بند «GitHub PAT معتبر» را
> به‌عنوان ورودی می‌خواست. نتیجه این شد که یک PAT با دسترسی `admin` در متن چت
> ثبت شد و طبق OC-11 عملاً معادل دسترسی کامل به تولید بود.
>
> **ترتیب ترجیح برای دادن دسترسی:**
> ۱. **Deploy key** — کلید خصوصی داخل سندباکس تولید می‌شود، فقط کلید عمومی در
>    Settings → Deploy keys ثبت می‌شود؛ پس از پایان کار حذف می‌گردد.
> ۲. **PAT با کمترین دامنه** — فقط همین مخزن، فقط Contents + Actions، انقضای کوتاه.
> ۳. اگر PAT در چت آمد: پس از پایان جلسه **حتماً revoke شود** (B-5).
>
> **هرگز در چت فرستاده نشود:** رمز FTP، محتوای `velora.env`، رمز دیتابیس،
> JWT/Encryption key، MetaAPI token. agent به هیچ‌کدام نیاز ندارد — §3 «قاعدهٔ Secret».
